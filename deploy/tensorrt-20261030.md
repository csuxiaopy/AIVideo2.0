## Multi-GPU thread validation

The first production attempt exposed an illegal-address error in the fire detector's cross-thread CUDA device context and was rolled back immediately. CUDA current-device state is thread-local: engines initialized on GPU 1 must also execute with GPU 1 current in background threads. The adapter now binds the configured CUDA device during engine warmup and each inference, serializes use of each engine, and restores the caller device afterwards.

The corrected adapter passed 336 fire/smoke calls from four executor threads on physical GPU 1, followed by 84 general detections explicitly routed across both physical GPUs. Both general workers confirmed TensorRT activation. The combined canary needs more than 5 GiB host RAM for its parent and two CUDA child processes; its successful validation used a 10 GiB limit.

## Build and rollback

Dockerfile.tensorrt pins the runtime/export dependencies. Build engines in an isolated GPU builder using scripts/export-tensorrt.py MODEL --batch 2 (general) or --batch 1 (fire/smoke), then replay production samples before publishing the engine and manifest together. Keep the same image size and class/threshold behavior.

Backup: /data/yolo_vlm_monitor/.deploy-backup-20261030-tensorrt. Previous image: yolo-vlm-gpu:before-tensorrt-20261030. New image: yolo-vlm-gpu:tensorrt-20261030. Runtime dependencies were bundled from the tested isolated container into the production image; surveillance samples, keys and database configuration were not included in the image.

To disable engines, set TENSORRT_ENABLED=false and recreate app through deploy/split.sh. To roll back the program, restore the previous image production tag and original compose.gpu.production.yml, then recreate only app. Web, database, model settings and audit records do not need migration or rollback. The original .pt weights remain available. Existing in-flight capture sessions reconnect once during app deployment.
